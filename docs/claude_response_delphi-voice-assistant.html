날짜:

⚠️ 편향 면책 문구
이 문서는 세 개의 LLM 팀(Claude / Gemini / OpenAI)이 각자의 관점에서 독립적으로 제안하고 교차 검토한 결과를 AI Facilitator가 합성한 것입니다. 실제 운영 환경, 사용자 요구사항, 조직 역량에 따라 결정이 달라질 수 있습니다. 본 문서를 기반으로 구현하기 전에 반드시 실제 워크로드 기반 검증을 수행하십시오.

1. Facilitator 합성

이번 Delphi 세션에서 세 팀은 개인용 보이스 비서 도구의 구조적 재설계라는 공통 목표를 향해 높은 수준의 수렴을 이루었습니다. 핵심 충돌 없이 역할 분리·확장성·음성 품질이라는 세 축에서 일관된 방향을 확정했습니다.

구조 측면에서는 Source Adapter → Event Processing → Speech Preparation → Delivery의 4레이어가 확정되었고, Adapter(변환)와 Router(라우팅)의 책임 분리, Policy Engine 3분리를 통해 Phase 1에서도 교체 가능한 내부 구조를 갖추기로 했습니다. CanonicalEvent 17필드 스키마는 이기종 소스(코딩 에이전트·Grafana)를 단일 계약으로 통합하는 근간이 됩니다.

음성 품질 측면에서는 8단계 Plugin Chain이 확정되었습니다. 2계층 언어 감지(global 글로벌 캐시 + local sliding window)와 Trie+LRU 기반 발음 사전(IT 용어 200개)이 Phase 1 품질의 핵심입니다. 언어 경계 break 범주형 정책과 Earcon acoustic decay는 청각 피로를 구조적으로 억제합니다. Expression Tag와 LLM 기반 동적 SSML은 Phase 3으로 연기했으며, 이는 Phase 1 릴리스 속도를 지키는 올바른 트레이드오프입니다.

운영 측면에서는 Phase 1부터 OTel 5 span + Prometheus /metrics를 도입해 "관측 없는 출시"를 방지합니다. DLQ DB 테이블과 히스테리시스 헬스 체크는 장애 가시성을 확보하며, Drain-and-Route 전환 전략은 Phase 2 이행의 연속성을 보장합니다.

5개의 보류 항목은 모두 권고안이 도출되었으며, 실제 구현 초기에 빠르게 결정 가능한 수준입니다. 근본적 이견이 아닌 세부 구현 기준 수준의 보류이므로 전체 아키텍처의 완성도는 높습니다.

2. 최종 확정 결정

A. 전체 아키텍처

A-1. 4레이어 파이프라인 확정 Phase 1
근거: Source Adapter → Event Processing → Speech Preparation → Delivery — 단방향 의존성으로 레이어별 독립 교체 가능. Event Router 분리(YAML/JSON 기반 라우팅 규칙)로 신규 소스 추가 시 코드 변경 최소화.
A-2. Policy Engine 3분리 Phase 1
근거: PolicyRules(불변/config) + PolicyStateStore(Protocol, 원자 check_and_mark_duplicate) + PolicyDecisionEngine. Phase 2 Redis 교체 시 호출부 코드 변경 없음.
A-3. CanonicalEvent 17필드 스키마 확정 Phase 1
근거: event_id, idempotency_key, fingerprint, dedupe_key, correlation_id, source, source_event_type, severity, priority_score, raw_text, language(LanguageProfile), ttl, interrupt_policy, version, metadata, trace_id. 이기종 소스를 단일 계약으로 통합.
@dataclass
class CanonicalEvent:
    event_id: str                    # UUID
    idempotency_key: str             # source+content 기반, 외부 주입
    fingerprint: str                 # content hash (dedupe)
    dedupe_key: str                  # 집계 윈도우 키
    correlation_id: str              # 연관 이벤트 체인
    source: str                      # "coding_agent" | "grafana"
    source_event_type: str           # 원본 이벤트 유형
    severity: Literal["critical","warning","info","resolved"]
    priority_score: int              # 0-100
    raw_text: str
    language: LanguageProfile
    ttl: int                         # 초
    interrupt_policy: Literal["interruptive","ambient","silent-summary"]
    version: str
    metadata: dict
    trace_id: str
    created_at: float = field(default_factory=time.time)

@dataclass
class LanguageProfile:
    primary: str          # BCP-47, 예: "ko"
    confidence: float     # 0.0-1.0
    script: str           # "Hangul" | "Latin" | "Mixed"
    mixed_content: bool   # 코드 스위칭 감지 여부

B. Source Adapter

B-1. 코딩 에이전트 인제스트 Phase 1
근거: POST localhost:8765/ingest/coding-agent, 2초 타임아웃, 예외 무시 (fire-and-forget). 서버는 큐에 push 후 즉시 202 반환. 에이전트 워크플로 블로킹 원천 차단.
B-2. Grafana 이중 수집 + 멱등성 Phase 1
근거: Webhook Primary + 30초 Polling Fallback. TTL 캐시 중복 제거(1차) + 영속 idempotency_key 기록(2차). 네트워크 분리 상황에서도 이벤트 유실 없음.
class SourceAdapter(Protocol):
    def to_canonical_event(self, raw: dict) -> CanonicalEvent: ...
    def source_id(self) -> str: ...
    def health_check(self) -> HealthStatus: ...

C. Event Queue

C-1. EventQueueProtocol 5메서드 확정 (seek_to_timestamp 제외) Phase 1
근거: publish(partition_key, ttl_ms) / consume(consumer_group, batch_size) / acknowledge / publish_to_dlq / get_metrics. seek_to_timestamp는 DLQ replay + TTL 자동 만료로 대체 — 실시간 도메인 anti-pattern.
class EventQueueProtocol(Protocol):
    async def publish(
        self, event: CanonicalEvent,
        partition_key: str | None = None,
        ttl_ms: int | None = None,
    ) -> str: ...                        # message_id 반환

    async def consume(
        self, consumer_group: str,
        batch_size: int = 1,
        max_wait_ms: int = 1000,
    ) -> list[QueuedEvent]: ...

    async def acknowledge(
        self, consumer_group: str, message_ids: list[str]
    ) -> None: ...

    async def publish_to_dlq(
        self, event: CanonicalEvent, reason: str,
        source_message_id: str | None = None,
    ) -> str: ...

    async def get_metrics(self) -> QueueMetrics: ...
C-2. 백프레셔 HWM=800 / LWM=200 Phase 1
근거: 도달 시 저우선순위 이벤트 거절 및 입력 속도 제한. 200 이하 복구 시 정상 모드. 큐 포화 전 업스트림 보호.
HIGH_WATER_MARK = 800   # 도달 시 저우선순위 이벤트 거절, 입력 속도 제한
LOW_WATER_MARK  = 200   # 복구 시 정상 처리 모드 재개

# Phase 1 운영 한계
PHASE1_LIMITS = {
    "max_adapters":          5,
    "max_events_per_second": 50,
    "max_queue_depth":       1000,
}

# Phase 2 전환 트리거
PHASE2_TRIGGERS = {
    "events_per_second":          200,
    "adapter_count":              10,
    "queue_depth_sustained_items": 500,
}
C-3. Phase 1→2 Drain-and-Route 전환 Phase 2
근거: 신규 publish는 Redis Streams로 전환, 기존 asyncio.Queue는 소진-only 모드 → 완전 소진 후 종료. 인메모리 이벤트 유실 없음.

D. Speech Preparation

D-1. 8단계 Plugin Chain 확정 (DAG-ready, 선형 실행) Phase 1
근거: LanguageDetection → SegmentSplitter → IdentifierNormalizer → PatternSuppressor → PronunciationDict → Normalization → ProsodyBoundaryInjection → SSMLAbstraction. 내부 DAG-ready 구조, 외부 선형 체인 호환.
PLUGIN_CHAIN = [
    LanguageDetectionPlugin,    # Tier1: global <5ms + Tier2: sliding window
    SegmentSplitterPlugin,
    IdentifierNormalizerPlugin, # snake_case→50ms | CamelCase→공백
    PatternSuppressorPlugin,    # IP/UUID→억제/축약
    PronunciationDictPlugin,    # Trie+LRU(10K), IT 용어 200개
    NormalizationPlugin,
    ProsodyBoundaryPlugin,      # 언어 경계 break: 20-40ms / 0-20ms / 60-120ms
    SSMLAbstractionPlugin,
]
D-2. 발음 사전 Trie+LRU(10K) Phase 1
근거: IT 용어 200개 시작. 용어 중심 통합 사전(언어별 ssml/reading/prosody). 조회 O(m) 보장. LRU 10K로 메모리 bounded.
D-3. 식별자·언어 경계 처리 정책 Phase 1
근거:
  • snake_case → 50ms silence padding (SSML <break>)
  • CamelCase → 공백 삽입
  • IP/UUID → 억제 또는 축약 ("아이피 주소", "유유아이디 식별자")
  • 언어 경계 break: 동일 스크립트 20-40ms / 유사 20ms 이하 / 이질 스크립트 60-120ms

E. TTS 라우팅 및 UX

E-1. TTS 우선순위 큐 + 교차 폴백 Phase 1
근거: Grafana FIRING > CodingAgent Stop > SubagentStop. SubagentStop→Supertonic, 나머지→EdgeTTS. 실패 시 교차 폴백, 전체 실패→텍스트+시각 알림. 단일 장애점 없음.
E-2. 인터럽션 4변수 함수 Phase 1
근거: f(severity × user_state × actionability × novelty). Critical interruptive는 역할/이름 인사 생략, 즉시 본론. Phase 1 user_state: 명시적 신호(DND, 앱 내 토글) + 타이핑 감지.
E-3. Earcon 4종 + Acoustic Decay Phase 1
근거: CRITICAL(하강3음) / HIGH(상승2음) / RESOLVED(상승3음) / SUMMARY(중립2음). 60초 내 동일 Earcon 반복 시 2회차 85%, 3회차 70%, 4회차+ tone brightness 저하. 새 cluster 발생 시 감쇠 리셋.
E-4. 요약: 최대 3건 + root cause 클러스터링 + 8초 fixed window Phase 1
근거: 첫 이벤트 수신 후 8초 고정 윈도우. 최대 3건 음성, 나머지 카운트. 동일 서비스/root cause → 1개 클러스터. 음성(판단/행동) vs 시각(근거/상세) 실시간 동기화.

F. 운영/관측성

F-1. OTel Phase 1부터 최소 프로파일 Phase 1
근거: ingest.receive / adapter.transform / router.dispatch / queue.enqueue+dequeue / sink.deliver — 5 span. Prometheus /metrics 엔드포인트 필수 노출.
F-2. DLQ DB 테이블 + failure_stage 세분화 Phase 1
근거: 8단계 failure_stage(ingest_parse ~ sink_delivery)로 장애 위치 즉시 파악. replay_status(pending/replayed/resolved/discarded).
CREATE TABLE event_dlq (
    dlq_id           TEXT PRIMARY KEY,
    event_id         TEXT NOT NULL,
    idempotency_key  TEXT,
    correlation_id   TEXT,
    source           TEXT,
    failure_stage    TEXT,   -- ingest_parse | adapter_transform |
                             -- idempotency_check | route_decision |
                             -- tts_primary | tts_fallback |
                             -- visual_notify | sink_delivery
    failure_reason   TEXT,
    payload_json     TEXT,
    attempt_count    INTEGER DEFAULT 0,
    first_failed_at  REAL,
    last_failed_at   REAL,
    replay_status    TEXT    -- pending | replayed | resolved | discarded
);
F-3. 소스 헬스 히스테리시스 Phase 1
근거: 3회 연속 실패→비정상 선언, 2회 연속 성공→복구. 플랩핑(flapping) 방지. 폴링 기본 + 선택적 heartbeat.
F-4. 설정 3레벨 프리셋 Phase 1
근거: Minimal(CRITICAL만 즉시) / Balanced(HIGH이상 맥락 기반, 기본값) / Proactive(NOC용 전체 알림). 초심자 프리셋 진입, 파워 유저 고급 설정 숨김 계층.

3. 미결 보류 항목 + 통합 권고안

B-1. PolicyStateStore 원자성 보장 수준
쟁점: asyncio 단일 루프 가정 vs ThreadPoolExecutor 혼용 시 레이스 컨디션
권고: Phase 1은 asyncio 이벤트 루프 단일 스레드로 제한. check_and_mark_duplicate()를 non-blocking async로 구현. 스레드 혼용 시 asyncio.Lock 명시적 주입. Protocol 문서에 선행 조건 명기.
B-2. 언어 감지 슬라이딩 윈도우 크기
쟁점: 윈도우 크기에 따른 과탐지(너무 작음) vs 반응 지연(너무 큼) 트레이드오프
권고: 기본값 min(N=10 이벤트, T=30초). cold-start 시 confidence=0.0 마킹 후 로컬 탐지 신뢰. language_detection.window_size 설정 파일 오버라이드 허용.
B-3. Earcon-TTS 시퀀싱 레이어 책임
쟁점: Earcon 완전 종료 후 TTS 시작 vs 오버랩 허용 — 레이어 책임 경계 불명확
권고: Earcon 메타데이터(earcon_type)는 Speech Preparation이 CanonicalEvent.metadata에 주입. 실제 시퀀싱(완전 종료 후 TTS, 오버랩 금지)은 Delivery 레이어 단독 책임. Speech Preparation은 힌트만 전달.
B-4. DLQ replay 트리거 방식
쟁점: 자동 replay vs 수동 트리거 전용, replay 순서 정책
권고: Phase 1은 수동 replay 전용 API(POST /admin/dlq/replay)만 구현. 순서: priority_score DESC + created_at ASC 복합 정렬. 자동 스케줄은 Phase 2 운영 경험 후 결정.
B-5. 요약 8초 윈도우 기산점
쟁점: "첫 이벤트 수신 후" vs "마지막 이벤트 후 침묵" — 이벤트 폭주 시 동작 크게 달라짐
권고: 첫 이벤트 수신 후 8초 fixed window 기준 채택. 8초 내 추가 이벤트는 동일 요약에 병합. summary.trigger_window_ms=8000 설정 파일 명시. high-churn source는 sliding window 실험을 telemetry flag로 A/B 검증.

5. 사후검증 체크리스트

반증 질문 (Falsification Questions)

  • 발음 사전 200개 적용 후 실제 청취 MOS(Mean Opinion Score)가 기준치(4.0 이상)를 달성하는가?
  • 8초 fixed window 요약이 이벤트 폭주(EPS=50) 상황에서 50% 이상의 클러스터링 압축율을 달성하는가?
  • Earcon acoustic decay 후에도 CRITICAL 인식률이 95% 이상 유지되는가?
  • Drain-and-Route 전환 중 메시지 유실률이 0이 되는가?
  • Hook 2초 타임아웃이 Claude Code 응답 지연에 실질적 영향을 주지 않는가?

선행 지표 (Leading Indicators)

발음 품질 사전 hit rate ≥ 80% (일별 Prometheus 집계)
인터럽션 정확도 Critical fast-track 비율 = CRITICAL 이벤트 수 (100% 일치)
DLQ 누적 dlq_entries_total 증가율 < 1건/시간 (정상 운영 기준)
큐 압력 queue_depth p99 < 500 유지
