빌트인 에이전트 사용법

subagent_type 파라미터의 두 출처 — 빌트인 vs 커스텀 에이전트의 차이와 활용법

Agent 툴의 두 가지 식별자

이전 통합 작업에서 agent-docs, agent-hook 같은 이름이 등장한 건 name 파라미터입니다. subagent_type과 다른 역할을 합니다.

name — 인스턴스 이름
  • 팀 리더가 이 에이전트에 붙이는 호출명
  • SendMessage의 to 필드에 사용
  • 자유롭게 지정 — 역할을 설명하면 됨
  • Claude Code 시스템과 무관한 레이블
subagent_type — 에이전트 유형
  • 어떤 시스템 프롬프트·툴셋을 쓸지 결정
  • 빌트인 타입 또는 .claude/agents/ 파일명
  • 지정 안 하면 claude (범용) 적용
  • 페르소나·툴 제한의 실제 출처
Agent 툴 파라미터 전체 구조
Agent({
  description: "짧은 설명 (로그에 표시)",   // UI 표시용
  subagent_type: "code-reviewer",          // ← 빌트인 or 커스텀 파일명
  name: "agent-review",                   // ← SendMessage 호출명 (자유 지정)
  model: "sonnet",                        // claude-sonnet-4-6
  team_name: "my-team",                   // TeamCreate로 만든 팀
  prompt: "작업 지시"                      // 이 에이전트에게 전달할 내용
})
이전 작업의 실제 구조:
name: "agent-rename" — 팀 리더가 SendMessage로 호출하는 이름
subagent_type: "claude" (또는 생략) — 범용 Claude 에이전트로 동작
즉, 에이전트 이름이 agent-기능 형태였던 건 naming convention이지, 특별한 타입이 아님

subagent_type의 두 출처

① 빌트인 에이전트
  • Claude Code에 내장된 전문 에이전트
  • 별도 파일 불필요 — 이름만 지정
  • 각자 특화된 시스템 프롬프트·툴 보유
  • 예: "code-reviewer", "planner"
② 커스텀 에이전트
  • .claude/agents/<name>.md 파일로 정의
  • 이 프로젝트에서 만든 feature-architect 등
  • 직접 툴 목록·행동 규칙 제어 가능
  • 빌트인과 동일한 방식으로 참조
// ① 빌트인 — Claude Code에 내장됨
Agent({ subagent_type: "code-reviewer", name: "agent-review", ... })

// ② 커스텀 — .claude/agents/feature-architect.md 파일 참조
Agent({ subagent_type: "feature-architect", name: "agent-arch", ... })

// ③ 생략 (= "claude") — 범용 에이전트
Agent({ name: "agent-rename", prompt: "..." })

빌트인 에이전트 실제 사용 패턴

단일 에이전트 — 전문 리뷰

// 보안 리뷰만 따로 돌릴 때
Agent({
  description: "보안 취약점 점검",
  subagent_type: "security-reviewer",  // 빌트인 OWASP 전문가
  name: "agent-sec",
  model: "sonnet",
  prompt: `
    src/auth/ 디렉토리의 보안 취약점을 분석하세요.
    완료 후 팀 리더에게 SendMessage로 심각도별 결과 보고.
  `
})

팀 구성 — 빌트인 + 커스텀 혼용

TeamCreate({ team_name: "full-feature" });

// ① 빌트인 — 설계 단계
Agent({
  subagent_type: "code-architect",   // 빌트인: 코드베이스 분석 후 청사진
  name: "agent-arch",
  prompt: "새 캐싱 레이어 설계. src/ 분석 후 팀 리더에게 설계 요약 전송."
});

// ② 커스텀 — 구현 단계 (설계 완료 후 spawn)
Agent({
  subagent_type: "feature-builder",  // 커스텀: .claude/agents/feature-builder.md
  name: "agent-build",
  prompt: "아키텍트 설계를 받아 구현. npm run build 확인 필수."
});

// ③ 빌트인 — 최종 리뷰
Agent({
  subagent_type: "typescript-reviewer",  // 빌트인: TS 타입 안전성 전문
  name: "agent-review",
  prompt: "변경된 파일 타입 안전성·async 패턴 검토. 심각도 분류 후 보고."
});
혼용의 이점:
빌트인은 검증된 전문 시스템 프롬프트를 제공합니다. 커스텀은 프로젝트 고유 규칙(빌드 명령, 금지 패턴 등)을 추가할 때 사용합니다.

언제 빌트인을 쓰고 언제 커스텀을 만드나

빌트인 에이전트로 충분한 경우
• code-reviewer — 일반 코드 리뷰
• security-reviewer — 보안 점검
• tdd-guide — 테스트 주도 개발
• 프로젝트 고유 규칙이 없을 때
• prompt에 추가 지시로 충분할 때
커스텀 에이전트가 필요한 경우
• 특정 툴만 허용해야 할 때 (보안)
• 프로젝트 고유 규칙 반복 적용
• npm run build 같은 고정 완료 조건
• 같은 역할을 여러 기능 개발에 재사용
• 빌트인에 없는 새 역할이 필요할 때
상황권장 선택이유
TS 타입 에러 수정 build-error-resolver (빌트인) 이미 최소 diff 원칙으로 설계됨
PR 보안 점검 security-reviewer (빌트인) OWASP 기준 내장, 별도 설정 불필요
이 프로젝트 기능 개발 설계 feature-architect (커스텀) Write 툴 제한, 완료 보고 규칙 포함
일회성 파일 이름 변경 작업 claude (기본) + 역할 프롬프트 단발성이라 파일 만들 필요 없음
Rust 빌드 에러 rust-build-resolver (빌트인) borrow checker 패턴 전문으로 훈련됨

이전 통합 작업의 실제 구조

agent-docs, agent-hook, agent-installer, agent-rename 이름의 의미를 풀면:

name subagent_type 역할 ───────────────────────────────────────────────────── agent-rename claude (기본) 파일 전체 siren→voice-persona 이름 변경 agent-hook claude (기본) hooks/ + src/index.ts Python 의존성 제거 agent-installer claude (기본) install.sh / uninstall.sh 신규 작성 agent-docs claude (기본) README.md 사용자 가이드 형식 재작성

모두 subagent_type을 생략(또는 "claude")한 범용 에이전트였고, name만 역할을 설명하는 이름으로 구분했습니다. 전문 빌트인 에이전트를 쓰지 않은 이유는 — 당시 작업이 "특정 언어 리뷰"나 "빌드 에러 수정"이 아닌 파일 내용 변경·신규 파일 작성이라 범용으로 충분했기 때문입니다.

빌트인 에이전트의 툴 제한 주의:
Explore, code-architect 같은 일부 빌트인은 읽기 전용 툴만 보유합니다. 파일을 수정해야 하는 작업에 이런 에이전트를 지정하면 Write 툴 없어 실패합니다. 작업 성격을 먼저 확인하고 선택하세요.
