워크플로우 스킬 — 개발 흐름 제어

brainstorming
superpowers자동 호출

아이디어를 완성된 설계와 스펙으로 발전시키는 협업 대화 스킬. 코딩 전에 반드시 거쳐야 하는 첫 번째 관문.

언제 사용하나
새 기능 추가, 컴포넌트 빌드, 동작 변경 등 창작성 작업 전 항상. "단순한 작업"이라도 생략 불가.
🔍 프로젝트 맥락 파악
→
❓ 질문 1개씩 (다지선다 선호)
→
🔀 2-3가지 접근 제안
→
📐 섹션별 설계 제시
→
📄 스펙 저장
→
writing-plans 전환
✦ Best Practice
  • "X를 추가해줘" 대신 "X를 어떻게 구현할지 brainstorming 해줘"로 시작
  • 스펙 파일은 docs/superpowers/specs/YYYY-MM-DD-기능명-design.md에 자동 저장
  • 설계 승인 전에 코드 작성 시작 — HARD-GATE로 차단됨
  • 복잡한 시스템이면 서브시스템으로 분리해 각각 brainstorm
writing-plans
superpowers자동 호출

스펙/요구사항을 체크박스 기반의 구체적 구현 플랜으로 변환. 각 단계는 2-5분짜리 단위 작업으로 세분화.

언제 사용하나
brainstorming으로 스펙 확정 후, 코드 수정 전. 보통 brainstorming이 자동으로 전환.
파일 구조 설계
→
Task별 플랜 작성
→
각 Task = 실패 테스트 작성 → 실행 → 구현 → 통과 → 커밋
→
자가 검토 후 저장
✦ Best Practice
  • 플랜 파일 경로: docs/superpowers/plans/YYYY-MM-DD-기능명.md
  • 실행 방법은 subagent-driven-development 권장, inline 실행은 executing-plans
  • 플랜 없이 멀티스텝 작업 시작 — 방향 잃기 쉬움
  • 플랜 자가검토: placeholder("TBD") 없는지, 타입 일관성 확인
subagent-driven-development
superpowers자동 호출

플랜의 각 Task를 독립된 서브에이전트에 위임해 실행. Task별로 스펙 준수 리뷰 → 코드 품질 리뷰 2단계 검토.

언제 사용하나
writing-plans로 플랜 완성 후 실행 시 기본 선택. 태스크가 독립적일 때 최적.
플랜 파일 읽기
→
TodoWrite 생성
→
구현 서브에이전트 파견
→
스펙 준수 리뷰어
→
코드 품질 리뷰어
→
Task 완료 표시
→
다음 Task 반복
✦ Best Practice
  • 구현 서브에이전트는 플랜 파일을 직접 읽지 않음 — 컨트롤러가 내용을 직접 전달
  • 서브에이전트가 질문하면 반드시 답변 후 재파견 (구현 시작 전)
  • 리뷰에서 문제 발견 시 무시하고 다음 단계 진행
  • 스펙 리뷰 → 코드 리뷰 순서 반드시 준수
  • 기계적 구현 Task: haiku 모델, 설계 판단 필요: opus 모델
executing-plans
superpowers수동 호출

동일 세션에서 인라인으로 플랜 실행. 서브에이전트 없이 Claude가 직접 체크포인트마다 검토.

언제 사용하나
Task가 서로 의존성이 있어 순차 실행이 필요할 때. subagent-driven보다 느리지만 컨텍스트 공유 가능.
✦ Best Practice
  • Task가 상호의존적일 때 (A의 결과를 B가 사용) selecting-plans 대신 이쪽
  • 체크포인트에서 테스트 통과 확인 후 다음 Task
  • 멀티스텝 작업을 체크포인트 없이 한 번에 실행
dispatching-parallel-agents
superpowers자동 호출

2개 이상의 독립 Task를 병렬 서브에이전트로 동시 실행해 속도를 높이는 스킬.

언제 사용하나
공유 상태 없이 독립적으로 처리 가능한 작업이 2개 이상일 때. 예: 프론트엔드 + 백엔드 동시 작업.
✦ Best Practice
  • 파일을 서로 수정하지 않는 완전히 독립적인 Task에만 적용
  • 병렬 에이전트는 git worktree를 각각 사용해 충돌 방지
  • 같은 파일을 두 에이전트가 동시 수정 — 반드시 충돌
finishing-a-development-branch
superpowers자동 호출

구현 완료 후 테스트 확인 → 4가지 선택지(로컬 머지/PR/유지/폐기)를 제시하고 worktree 정리.

언제 사용하나
모든 Task 완료 + 테스트 통과 후. subagent-driven-development가 자동으로 이 스킬로 전환.
테스트 실행·확인
→
환경 감지 (worktree 여부)
→
옵션 제시
① 로컬 머지 → ② PR 생성 → ③ 현상 유지 → ④ 폐기(확인 필요)
✦ Best Practice
  • PR 선택 시 worktree 보존 — 피드백 반영 가능
  • 폐기 시 "discard" 직접 타이핑 확인 필요
  • 테스트 실패 상태에서 머지 진행
  • worktree가 .worktrees/ 하위인 경우만 자동 정리

개발 품질 스킬

test-driven-development
superpowers자동 호출

테스트 먼저 작성 → 실패 확인 → 최소 구현 → 통과 → 리팩터링 사이클을 강제하는 스킬.

언제 사용하나
기능 구현 또는 버그픽스 전. 구현 코드 작성 전 테스트가 먼저 나와야 함.
실패 테스트 작성
→
실패 확인 (red)
→
최소 구현
→
통과 확인 (green)
→
리팩터 (refactor)
✦ Best Practice
  • 테스트를 먼저 커밋 후 구현 커밋 — 리뷰어가 설계 의도 파악 가능
  • 경계 케이스부터 테스트 (빈 입력, null, 최댓값)
  • 모든 기능을 다 구현한 뒤 테스트 추가 — TDD 원칙 위반
  • 테스트 하나가 하나의 행위만 검증
systematic-debugging
superpowers자동 호출

버그·테스트 실패 발생 시 추측이 아닌 증거 기반으로 체계적으로 근본 원인을 찾는 스킬.

언제 사용하나
버그, 예상치 못한 동작, 테스트 실패 발생 시. 수정 제안 전 반드시 먼저 진단.
증상 정확히 기술
→
재현 조건 확인
→
로그/스택트레이스 분석
→
가설 수립
→
증거로 검증
→
수정 후 재현 테스트
✦ Best Practice
  • 스택 트레이스 전체를 읽고 근본 원인 파일·라인 특정
  • 에러 메시지 보고 추측으로 수정 시도
  • 불명확하면 로그 추가 → 재실행 → 확인 → 수정 순서
  • 수정 후 동일 조건에서 버그가 재현되지 않음을 확인
requesting-code-review
superpowers자동 호출

작업 완료 또는 머지 전 코드 리뷰를 요청. 리뷰어 서브에이전트 파견 및 피드백 수집.

언제 사용하나
Task 완료, 주요 기능 구현 후, 머지 전. subagent-driven-development 마지막 단계에서 자동 호출.
receiving-code-review
superpowers자동 호출

리뷰 피드백을 맹목적으로 따르지 않고 기술적으로 검증한 후 적용하는 스킬.

언제 사용하나
코드 리뷰 피드백 수신 시. 특히 기술적으로 불명확하거나 의심스러운 제안에 대해.
✦ Best Practice
  • 피드백에 동의하기 전 실제 코드에서 검증
  • 모든 리뷰 코멘트를 비판 없이 즉시 적용 — 잘못된 제안도 있음
  • 동의하지 않으면 근거와 함께 반론 제시
verification-before-completion
superpowers자동 호출

"완료했습니다"라고 선언하기 전 실제로 검증 명령을 실행하고 결과를 확인하는 스킬. 증거 없는 성공 주장 금지.

언제 사용하나
작업 완료 주장 전, 커밋 전, PR 생성 전. 자동으로 강제됨.
✦ Best Practice
  • 테스트 실행 결과를 직접 인용해 보고
  • "구현했으므로 동작할 것입니다" — 실행 전 성공 주장
  • 빌드 + 테스트 + 타입체크 순서로 모두 통과 확인
using-git-worktrees
superpowers자동 호출

현재 작업과 격리된 git worktree를 생성해 실험적 작업이나 플랜 실행을 안전하게 진행.

언제 사용하나
기능 작업 시작 전 격리가 필요할 때, 플랜 실행 전. 기본적으로 .claude/worktrees/에 생성.
✦ Best Practice
  • 메인 브랜치를 건드리지 않고 실험 가능
  • 병렬 에이전트마다 별도 worktree 사용
  • worktree 생성 후 직접 cd로 이동 — EnterWorktree 도구 사용
  • 작업 완료 시 finishing-a-development-branch로 정리

/save-session
수동 호출

현재 세션의 작업 내용(무엇을 만들었고, 무엇이 실패했고, 무엇이 남았는지)을 날짜 파일로 저장. 다음 세션에서 이어받기 위한 컨텍스트 보존.

언제 사용하나
세션 종료 전, 복잡한 디버깅 중간, 컨텍스트 한계에 도달하기 전. 
/save-session
✦ Best Practice
  • 저장 경로: ~/.claude/session-data/YYYY-MM-DD-abc123-session.tmp
  • "무엇이 실패했나" 섹션이 가장 중요 — 다음 세션이 같은 실수 반복 방지
  • 장기 작업 시 매일 종료 전 실행
  • PR 링크, 커밋 목록 등 코드로 확인 가능한 정보는 저장 불필요
/resume-session
수동 호출

가장 최근 저장된 세션 파일을 로드해 이전 작업 맥락을 완전히 복원.

언제 사용하나
새 세션에서 전날 작업을 이어받을 때 제일 먼저 실행. 
/resume-session
✦ Best Practice
  • 새 세션 시작 후 가장 먼저 실행 → 작업 시작 전 컨텍스트 확보
  • 특정 날짜 파일을 지정해 불러올 수도 있음
  • 복원 후 현재 코드 상태 확인으로 저장 내용의 정확성 검증
/checkpoint
수동 호출

작업 중간에 현재 상태를 체크포인트로 저장. 검증 실행 후 상태를 기록.

언제 사용하나
장기 작업 중간에 "여기까지는 성공" 지점을 표시할 때.

Hookify 시스템 — 행동 규칙 자동화

/hookify
수동 호출

특정 행동(파일 편집, git push, bash 실행 등)을 Claude가 할 때 자동으로 규칙을 실행하거나 차단하는 훅을 만드는 시스템. 반복적인 실수를 구조적으로 방지.

언제 사용하나
Claude가 반복하는 실수 패턴을 발견했을 때. 인자 없이 실행하면 대화를 분석해 자동 추천. 
/hookify                          # 대화 분석 후 자동 추천
/hookify "프로덕션 DB 직접 수정 금지"  # 명시적 규칙 생성
✦ Best Practice
  • 반복되는 불필요한 행동을 발견하면 바로 /hookify로 규칙화
  • 세션 종료 전 /hookify 실행 → 이번 세션의 문제 행동 자동 감지
  • 규칙은 ~/.claude/settings.json의 hooks에 저장
  • 훅이 너무 많아지면 정상 동작도 차단될 수 있음 — 주기적 정리
/hookify-configure  /hookify-list  /hookify-help
수동 호출

기존 훅 목록 확인, 활성화/비활성화, 도움말 제공.

/hookify-list        # 설정된 모든 훅 목록
/hookify-configure   # 훅 활성화/비활성화 토글
/hookify-help        # Hookify 전체 문서

  • /prp-plan은 코드베이스 분석 + 패턴 추출 후 상세 구현 플랜 생성
  • /prp-implement는 검증 루프 포함 — 에러 시 자동 재시도
  • /prp-commit은 자연어로 파일 특정 가능 ("테스트 파일만 커밋")
  • /prp-pr은 PR 템플릿 자동 발견 + 변경 분석 + 푸시까지 자동화

GitNexus — 코드 지식 그래프 스킬

GitNexus 스킬군 (7개)
자동 호출

코드베이스를 지식 그래프로 인덱싱하고 심볼 간 관계, 실행 흐름, 영향 분석을 수행. Cypher 쿼리 기반.

gitnexus-cli
  • 레포 인덱싱, 상태 확인, 위키 생성
  • "이 레포 분석해줘", "인덱스 재구축"
gitnexus-exploring
  • 코드 동작 이해, 아키텍처 탐색
  • "X는 어떻게 동작해?", "인증 흐름 보여줘"
gitnexus-debugging
  • 버그 추적, 에러 근원 탐색
  • "왜 X가 실패해?", "이 에러 어디서 나오는지"
gitnexus-impact-analysis
  • 변경 영향도 분석 (blast radius)
  • "X를 바꾸면 무엇이 깨져?", "안전한지 확인"
gitnexus-refactoring
  • 안전한 이름 변경, 추출, 이동
  • "함수 이름 변경", "모듈로 추출"
gitnexus-pr-review
  • PR 변경사항 분석, 위험 평가
  • "PR #42 리뷰", "이 PR 머지 안전한지"
✦ Best Practice
  • 대규모 리팩터링 전 gitnexus-impact-analysis로 영향도 먼저 확인
  • 새 코드베이스 탐색 시 gitnexus-cli로 인덱싱 먼저
  • 함수 이름 변경 시 gitnexus-refactoring이 모든 참조를 자동 발견
