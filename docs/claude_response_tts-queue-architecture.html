TTS 큐 기반 아키텍처 분석

제안된 구조: 각 에이전트가 WAV를 즉시 생성 → 공유 큐에 추가 → 단일 소비자가 순서대로 재생

핵심 전제: 프로세스 격리 문제

현재 실행 모델
서브에이전트 종료 시마다 OS가 새 프로세스를 생성: node dist/index.js subagent-stop ← 에이전트 A 종료 node dist/index.js subagent-stop ← 에이전트 B 종료 (별개 프로세스) node dist/index.js subagent-stop ← 에이전트 C 종료 (별개 프로세스) node dist/index.js ← MCP 서버 (stdio, 지속 실행)
인메모리 큐는 공유 불가
각 subagent-stop 프로세스는 독립된 메모리 공간을 가집니다. 프로세스 A가 JS 배열에 WAV를 push해도 프로세스 B는 볼 수 없습니다. "메모리 큐"를 쓰려면 모든 프로세스가 접근 가능한 공유 메모리 경계가 필요합니다.

큐 구현 방안 비교

방안 A — MCP 서버 프로세스 내 HTTP 큐 엔드포인트

동작 흐름
subagent-stop 프로세스 MCP 서버 (지속 실행, 포트 7779) ────────────────────── ────────────────────────────── 1. speakSupertonic() → WAV 생성 (즉시) 2. POST /tts-queue { wav, voice, speed } → 큐에 push 3. 프로세스 종료 큐 소비자: afplay 순차 재생 → 재생 완료 후 다음 항목
장점
  • 별도 프로세스/포트 없음 — MCP 서버에 Express/http 엔드포인트 추가만으로 구현
  • WAV 생성(병렬)과 재생(순차)이 완전히 분리됨 — 에이전트는 생성 즉시 종료 가능
  • 진짜 FIFO — 도착 순서대로 재생
제약
  • MCP 서버가 현재 stdio 전용 — HTTP 포트를 추가로 열어야 함
  • MCP 서버 재시작 시 큐 소실 (비지속)
  • WAV 버퍼를 HTTP 바디로 전송 — 큰 파일은 메모리 pressure

방안 B — 파일 스풀 디렉터리 (가장 단순)

동작 흐름
subagent-stop 프로세스 TTS 재생 데몬 (별도 프로세스) ────────────────────── ────────────────────── 1. WAV 생성 → /tmp/tts-spool/ inotifywait or 폴링 <timestamp>_<voice>.wav ← 새 파일 감지 2. 메타(voice, speed) JSON 파일 쓰기 → 큐에 추가, 순서대로 afplay 3. 프로세스 종료
장점
  • 프로세스 간 통신이 파일 시스템 — 추가 포트·서버 없음
  • 크래시 내성 — 스풀에 남은 파일은 다음 실행에서 소비 가능
  • 현재 코드 변경 최소화
제약
  • 별도 데몬 프로세스 필요 (server.sh 또는 launchd)
  • macOS에서 inotifywait 없음 → fswatch 또는 폴링 필요
  • 타임스탬프 기반 정렬이 실제 큐 순서와 다를 수 있음 (밀리초 충돌)

방안 C — 전용 TTS 큐 서버 (포트 7779)

동작 흐름
subagent-stop 프로세스 TTS 큐 서버 (포트 7779) ────────────────────── ────────────────── 1. WAV 생성 (즉시) 2. POST /enqueue { wav_b64, voice } → FIFO 큐 push 3. 종료 소비자 goroutine: afplay 순차
장점
  • MCP 서버와 완전 분리 — 각자 독립 배포
  • 큐 상태 API(GET /queue) 추가 가능 → 모니터링 용이
제약
  • 관리할 프로세스가 하나 더 늘어남 (server.sh 관리 필요)
  • WAV 바이너리를 Base64로 HTTP 전송 → 33% 크기 증가

현재 잠금 방식 대비 실질적 이득

항목현재 (withTTSLock 폴링)큐 기반
에이전트 대기 시간 재생이 끝날 때까지 프로세스가 살아 있음 (최대 25초+) WAV 생성 후 즉시 종료 → 빠른 반환
동시 발화 위험 있음 — withTTSLock 버그 2개로 인해 acquired=false 상태에서 fn() 실행 가능 없음 — 소비자가 단 하나
FIFO 순서 보장 비보장 — OS 타이머로 결정 보장 — 큐 도착 순서
타임아웃 시 발화 누락 25초 초과 시 발화 안 됨 큐 길이 제한이 없는 한 누락 없음
구현 복잡도 현재 코드 그대로 중간 — 큐 서버 또는 스풀 데몬 필요
WAV 생성 타이밍 잠금 내부에서 생성 + 재생 (직렬) 생성 병렬, 재생 직렬 → 전체 지연 감소

시나리오 비교 (에이전트 3개 동시 종료)

현재 방식 (총 약 19초)

t=0 에이전트 A: 잠금 획득, WAV 생성(2s) + 재생(7s) t=0 에이전트 B: 잠금 대기 (폴링 300ms) t=0 에이전트 C: 잠금 대기 (폴링 300ms) t=9 에이전트 A: 잠금 해제, 종료 t=9.3 에이전트 B: 잠금 획득, WAV 생성(2s) + 재생(5s) t=16 에이전트 B: 종료 t=16 에이전트 C: 잠금 획득, WAV 생성(2s) + 재생(4s) t=22 에이전트 C: 종료 ──────────────────────────────────────────────────── 총 대기: A=0s, B=9s, C=16s / 전체: ~22s

큐 기반 방식 (총 약 18초, 에이전트는 즉시 종료)

t=0 에이전트 A: WAV 생성(2s) → 큐 push → 종료 (t=2s) t=0 에이전트 B: WAV 생성(2s) → 큐 push → 종료 (t=2s) t=0 에이전트 C: WAV 생성(2s) → 큐 push → 종료 (t=2s) ↓ t=0 큐 소비자: A 재생(7s) t=7 B 재생(5s) t=12 C 재생(4s) → t=16 완료 ──────────────────────────────────────────────────── 에이전트 대기: 모두 ~2s (WAV 생성 시간만) 전체 재생: ~16s / 에이전트 자원 해제: t=2s

권장 구현 방향

단기 (버그 수정 우선)
withTTSLock의 두 버그(ENOENT break, 타임아웃 후 fn() 실행)를 먼저 수정합니다. 현재 구조에서 동시 발화 위험을 제거하는 가장 빠른 방법입니다.
중기 — 방안 B (파일 스풀 + 데몬) 권장
  • subagent-stop: WAV 생성 → /tmp/tts-spool/에 파일 기록 → 즉시 종료
  • tts_server/tts_player_daemon.sh: while + sleep 0.5 폴링, 파일 도착 순서대로 afplay
  • server.sh에 데몬 시작/종료 추가
  • 파일명: <epoch_ms>_<voice>.wav + 같은 이름 .meta.json(speed)
#!/usr/bin/env bash
# tts_player_daemon.sh — 스풀 디렉터리에서 WAV를 순서대로 재생
SPOOL=/tmp/tts-spool
mkdir -p "$SPOOL"
while true; do
  # epoch_ms 순서로 정렬된 첫 번째 WAV
  wav=$(ls -1t "$SPOOL"/*.wav 2>/dev/null | tail -1)
  if [[ -n "$wav" ]]; then
    meta="${wav%.wav}.meta.json"
    speed=$(python3 -c "import json,sys; print(json.load(open('$meta'))['speed'])" 2>/dev/null || echo "1.2")
    afplay -r "$speed" "$wav" && rm -f "$wav" "$meta"
  else
    sleep 0.5
  fi
done
// subagent-stop 측 변경: WAV 생성 후 스풀에 기록하고 즉시 반환
async function enqueueTTS(wav: Buffer, voice: string, speed: number): Promise {
  const ts = Date.now();
  const base = `/tmp/tts-spool/${ts}_${voice}`;
  writeFileSync(`${base}.wav`, wav);
  writeFileSync(`${base}.meta.json`, JSON.stringify({ voice, speed }));
}
// withTTSLock 불필요 — 데몬이 단일 소비자
결론: 제안한 구조는 방향이 옳습니다.
단, "인메모리 큐"는 프로세스 격리 때문에 구현 불가 → 파일 스풀 방식(방안 B)이 가장 단순하고 안정적입니다. 단기에는 withTTSLock 버그 수정, 중기에는 스풀 데몬으로 전환을 권장합니다.
