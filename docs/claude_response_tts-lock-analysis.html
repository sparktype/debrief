withTTSLock 동작 분석

여러 에이전트 프로세스가 동시에 발화를 시도할 때 withTTSLock이 어떻게 동작하는지 분석합니다.

결론 요약

질문실제 동작판정
동시 발화가 완전히 막히는가? 타임아웃 또는 readFileSync 오류 시 잠금 없이 실행됨 불완전
대기 에이전트가 순서대로 발화되는가? 순서 보장 없음 — OS 스케줄링에 의해 결정됨 비보장
대기 중인 발화가 누락되는가? 타임아웃(25초) 이내면 발화됨, 이후는 잠금 없이 실행 정상 범위 내

버그 1 — 타임아웃 후에도 발화 실행 (잠금 없이)

async function withTTSLock<T>(fn: () => Promise<T>): Promise<T> {
  const deadline = Date.now() + LOCK_WAIT_MS;   // 25초
  let acquired = false;
  while (!acquired) {
    try {
      const fd = openSync(TTS_LOCK_FILE, "wx");
      ...
      acquired = true;
    } catch {
      ...
      if (Date.now() > deadline) break;          // ← acquired = false 인 채로 탈출
      await new Promise(r => setTimeout(r, 300));
    }
  }
  try {
    return await fn();    // ← acquired = false 여도 실행!
  } finally {
    if (acquired) try { unlinkSync(TTS_LOCK_FILE); } catch { }
  }
}
문제: 25초를 기다렸는데 잠금을 못 얻으면 break → acquired = false 인 채로 fn()이 실행됩니다. 잠금 보유자(리더)가 아직 발화 중인 경우 동시 발화가 발생합니다.

문제: 잠금 파일을 읽는 도중 다른 프로세스가 파일을 삭제하면 readFileSync가 ENOENT를 던집니다. 이때 break로 탈출해 acquired = false인 채로 fn()이 실행됩니다. 다음 루프에서 다시 openSync("wx")를 시도해야 올바른 동작입니다.

순서 보장 문제

FIFO 순서 보장 없음: 여러 에이전트가 300ms마다 openSync("wx")를 시도합니다. 잠금이 해제될 때 먼저 대기하고 있었던 에이전트가 우선권을 갖지 않습니다. OS 타이머와 스케줄러가 누가 먼저 파일 생성에 성공하는지를 결정합니다.
실용적 관점: TTS는 각 에이전트가 3~10초 발화하므로 순서가 바뀌어도 큰 문제가 없습니다. "리뷰어 다음 플래너" vs "플래너 다음 리뷰어"는 사용자 경험에 영향이 적습니다. 완전한 FIFO가 필요하다면 별도 큐 파일이 필요합니다.

수정 방법

버그 1·2 수정 — break → continue, 타임아웃 시 skip

async function withTTSLock<T>(fn: () => Promise<T>): Promise<T> {
  const deadline = Date.now() + LOCK_WAIT_MS;
  let acquired = false;
  while (!acquired) {
    try {
      const fd = openSync(TTS_LOCK_FILE, "wx");
      writeSync(fd, String(Date.now()));
      closeSync(fd);
      acquired = true;
    } catch {
      // 잠금 파일 읽기 실패(ENOENT 등) → 다음 루프에서 재시도 (break 아님)
      try {
        const t = parseInt(readFileSync(TTS_LOCK_FILE, "utf-8"), 10);
        if (isNaN(t) || Date.now() - t > LOCK_STALE_MS) {
          unlinkSync(TTS_LOCK_FILE);
        }
      } catch { /* ENOENT: 다음 루프에서 openSync 재시도 */ }

      if (Date.now() > deadline) {
        // 타임아웃 — fn()을 실행하지 않고 조용히 포기
        return undefined as T;
      }
      await new Promise(r => setTimeout(r, 300));
    }
  }
  try {
    return await fn();
  } finally {
    try { unlinkSync(TTS_LOCK_FILE); } catch { /* 무시 */ }
  }
}
변경 포인트:
  • catch { break } → catch { /* continue */ } — ENOENT 시 다음 루프에서 openSync 재시도
  • 타임아웃 → return undefined — 잠금 없이 발화하지 않음 (음성 스킵)
  • if (acquired) 가드 제거 — finally는 항상 획득 상태이므로 무조건 해제
