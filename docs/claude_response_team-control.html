팀 구성 — 누가 결정하는가

Claude Code가 자율 판단하는 것과 사용자가 제어하는 것의 경계

결론부터: 팀의 세부 구성(에이전트 수·타입·의존성·병렬성)은 Claude Code(팀 리더)가 자율 판단합니다. 단, 사용자는 여러 레버로 그 판단에 영향을 줄 수 있습니다.

Claude Code가 자율 판단하는 것

사용자가 "팀을 구성하여 진행합니다"라고 말하면, 아래 모든 것을 Claude Code가 스스로 결정합니다.

결정 항목판단 근거예시
에이전트 수 작업 분해 후 독립 가능한 단위 수 4개 파일 독립 수정 → 에이전트 4명
각 에이전트의 subagent_type 작업 성격 (리뷰·구현·탐색 등) 코드 분석 → Explore, 리뷰 → code-reviewer
Task 분해 방식 의존 관계·파일 충돌 분석 설계 완료 후 구현 시작 → blockedBy 설정
병렬 vs 순차 Task 의존성 그래프 파일 겹침 없으면 동시 spawn
각 에이전트의 prompt 내용 전체 목표 + 해당 Task 범위 담당 파일·완료 조건·보고 형식 포함
사용자 입력 "공개 배포용 원클릭 설치 스크립트 추가. 훅 최적화도 포함. 팀 구성하여 진행." Claude Code의 자율 판단 → 작업 분해: install.sh 신규 / hooks 최적화 / 이름 변경 / 문서화 (4개) → 파일 충돌 분석: hooks 담당과 index.ts 담당이 겹침 → 분리 필요 → 병렬 가능: install.sh ↔ rename 작업은 독립적 → 동시 spawn → subagent_type: 전부 파일 수정 작업 → "claude" (범용) 선택 → Task 의존성: rename 완료 후 문서화 → blockedBy 설정

사용자가 팀 구성에 영향을 주는 레버

직접 "에이전트 3명으로 구성해"라고 명령할 수도 있고, 간접적으로 환경을 설계해 Claude Code의 판단을 유도할 수도 있습니다.

📝
레버 ① — 프롬프트에 직접 지시
가장 강력한 레버. "N명 팀", "병렬로", "워크트리에서", "설계 후 구현 순서로" 등을 명시하면 Claude Code가 그대로 따릅니다.

"설계 → 구현 → 테스트 3단계로 팀 구성하여 진행합니다."
→ 3명, 순차 의존성 설정
📁
레버 ② — .claude/agents/ 파일 사전 정의
feature-architect.md처럼 파일을 만들어두면, Claude Code가 설계 작업을 판단할 때 그 파일을 subagent_type으로 선택할 가능성이 높아집니다. 행동 규칙·툴 제한이 자동 적용되므로 prompt가 짧아져도 됩니다.
📄
레버 ③ — CLAUDE.md 제약 조건
모델 제한(model: "sonnet"만), 네이밍 규칙, 작업 원칙(YAGNI, 빌드 확인 필수 등)을 CLAUDE.md에 정의하면 Claude Code가 팀 구성 시 이 규칙을 반영합니다.
🔄
레버 ④ — 중간 개입·승인
Plan 모드(/plan)를 사용하면 Claude Code가 팀 구성 계획을 먼저 제시하고 승인을 기다립니다. 팀 구성이 마음에 들지 않으면 수정 요청 가능.

제어 수준 스펙트럼

어떻게 요청하느냐에 따라 사용자 제어 vs Claude Code 자율성의 비중이 달라집니다.

요청 방식Claude Code 자율성사용 상황
"팀 구성하여 진행합니다." 최대 — 모든 것을 스스로 판단 신뢰하고 맡길 때
"설계 → 구현 → 리뷰 순서로 팀 구성." 중간 — 구조는 고정, 세부는 자율 단계 순서가 중요할 때
"feature-architect, feature-builder, feature-reviewer 3명으로." 낮음 — 타입·수까지 지정 정확한 역할이 이미 설계됐을 때
직접 Agent() 코드 작성 없음 — 사용자가 직접 구성 고정 템플릿으로 반복 실행할 때

Claude Code가 스스로 판단하기 어려운 것

다음 상황에서는 Claude Code의 자율 판단이 빗나가기 쉽습니다. 프롬프트에 명시적으로 알려주거나 CLAUDE.md에 규칙을 넣어두는 게 좋습니다.

알려줘야 잘 하는 것
  • 이 파일들은 동시 수정하면 충돌 남
  • 사내 환경이라 Opus 모델 사용 불가
  • 빌드 명령이 npm run build가 아님
  • 테스트 실행에 특수 환경변수 필요
  • 특정 파일은 건드리지 말 것
잘 추론하는 것
  • 어떤 파일이 독립적으로 수정 가능한지
  • 설계 전 탐색이 필요한지
  • 리뷰 단계가 필요한지
  • Task 간 의존 순서
  • 적절한 에이전트 수 (과도하게 늘리지 않음)
모델 제한은 반드시 명시하세요.
HMG 사내 환경처럼 특정 모델만 쓸 수 있는 경우, CLAUDE.md에 model: "sonnet"만 사용하라고 적어두지 않으면 Claude Code가 Opus를 선택할 수 있습니다.

실전 요약

기본 전략:
"팀 구성하여 진행합니다"만으로 Claude Code에게 맡기되, .claude/agents/ 파일로 역할별 행동 규칙을 사전에 제약해두면 자율 판단의 품질이 높아집니다.

구조가 틀렸을 때는 다음 프롬프트에서 "이번엔 설계자 1명 + 구현자 2명 병렬로" 같이 보정하면 됩니다. Claude Code는 이전 판단을 고집하지 않습니다.
